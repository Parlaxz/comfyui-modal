3. ROOT CAUSE - AUDITED (replaces the earlier warm-reuse wording)
======================================================================
REFRAMING PER USER CORRECTION:
  The Run 2 benchmark task was fresh/cold. The shared container/session id
  (95f1d1c0a5444ec1 appearing in both the probe output and Run 2's trace)
  proves PROVENANCE OF THE FROZEN BASELINE STATE, not warm-container reuse,
  and is not the cause of anything by itself.

A. WRITERS / READERS of runtime_config_generation.json (full inventory)
   Writer (exactly ONE production path):
     RuntimeBootstrap.finalize_runtime_state_generation (runtime_bootstrap.py:1642)
       -> write_runtime_state_generation_marker (runtime_generation.py:144)
       called ONCE at snapshot construction (modal_app.py:9857, snap=True path),
       with NO explicit generation => content-derived token.
     (runtime_bootstrap.py:1296-1327 are constructor DI bindings with these
      module functions as defaults - not additional writers.)
   Reader (exactly ONE production authority):
     RuntimeBootstrap._decide_runtime_state_reload (runtime_bootstrap.py:1722,
     reader at :1748) - the restore-time guard; decides skip vs fail-closed
     Volume.reload(). verify_runtime_state_manifest (:1776) validates file
     bytes only after token equality.

B. WHY TWO CONSTRUCTIONS OF THE SAME DEPLOYMENT PRODUCED DIFFERENT TOKENS
   The deployed derivation IS content-derived (_content_derived_generation,
   runtime_generation.py:132-141,175: sha256 over the canonical manifest of
   tracked-file sha256s). Prior R42 state (report line 46) claims "volatile
   fields excluded by construction". AUDIT RESULT: that holds for the MANIFEST
   STRUCTURE but NOT for the HASHED FILE BYTES:
     - gpu_capacity_frozen.json payload embeds "captured_at": time.time()
       (restore_memory_arm.py:130-135) and provider-dependent gpu_name.
       Its sha256 therefore differs on EVERY construction (observed:
       e9c1418ef132 in Construction A vs c3db8a43a9d8 in Construction B).
     - prescan_custom_nodes.json bytes also differed between the two observed
       same-deployment constructions (197341948867 vs 67aa041b548c); the exact
       volatile field inside the prescan payload is not yet located (writer
       not audited) but the divergence is measured fact.
   A volatile byte anywhere in a tracked file poisons its sha256 -> poisons
   the manifest -> rotates the "content-derived" token per construction.
   Observed tokens are therefore explained WITHOUT any randomness regression:
   token = f(file bytes), and file bytes are not immutable per deployment.

C. FAILURE MECHANISM (deterministic given the state layout)
   Each snapshot-build container freezes ITS OWN construction token into the
   snapshot instances it prepares; the shared volume marker holds only the
   LATEST construction's token. With >=2 same-deployment constructions alive
   (here: A=95f1d1... AWS 18:07:54Z, B=d28091b... GCP 18:09:51Z during final
   gate prep), a request executing in/restoring state from a NON-latest
   construction compares stale-expected != volume-current and fail-closes to
   reload_runtime_state (~106 ms) -> RuntimeStatus DEGRADED.
   Run 1 skipped ONLY because its serving construction (B) was also the last
   volume writer. Run 2 failed because its serving construction (A) was not.
   This is placement-independent (would occur single-provider) and independent
   of probe timing or Volume visibility.

D. SOURCE-PROBE MUTATION: PROVEN NO
   1. Zero trace events in the 18:10:00-18:30:30Z window across BOTH retained
      traces - the probe performed no construction and no writes.
   2. The volume marker still held Construction B's token (9faa3a03...) at
      Run 2's check - unchanged since 18:09:51Z, i.e. untouched by the probe.
   3. Code: source_identity_probe (modal_app.py:16676) is read-only (SHA over
      imported module files; no model init, no flag mutation); construction +
      marker finalize run only on the snap=True snapshot-build path, which a
      method-only probe invocation does not trigger.
   The probe's role in this incident is limited to REVEALING the session id
   that made provenance traceable. It did not cause the failure.

E. DETERMINISM GUARANTEE - CURRENT ANSWER: NOT GUARANTEED
   An unchanged deployment/image/source does NOT yield the same expected
   generation across cold boots/providers today, because tracked-file BYTES
   vary per construction (captured_at; provider-dependent gpu_name; prescan
   volatility). The guarantee becomes true only if every manifest-tracked
   file is byte-immutable for one deployment content (volatile fields stripped
   or moved out-of-band, provider-variable fields normalized or excluded).
