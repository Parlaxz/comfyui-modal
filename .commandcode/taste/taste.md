# Taste
See [taste/taste.md](taste/taste.md)

- For benchmark validation runs, insists on structural validity for comparability: a run that hits a construction container's first request instead of a reused-snapshot restored container is invalid and must be repeated, and other platform variances (e.g., region) must be checked against the baseline. Container-state variance cuts both ways: a run that lands on a WARM reused container (Fresh: NO, restore_count > 1, same container_session_id/restored_instance_id as a prior run) is not a cold run and must not be counted toward a requested number of cold runs — repeat until a genuinely fresh container is obtained rather than accepting the warm run. Confidence: 0.85
- Wants silent gate failures to be impossible: any conditional feature that can reject a path must emit explicit telemetry with the exact reason (e.g., `speculative_skip` events), so a non-exercised feature is provably diagnosable from the artifact; required telemetry lists the exact fallback/rejection reason fields for the next run. Confidence: 0.85

- When the user tells them to stop hallucinating and work factually (terse frustration, e.g., "please for fucks sake stop hallucinating and only work factually. get it working and finish up"), responds with a short acceptance plus an enumeration of ONLY the currently verifiable facts, then proceeds immediately to verify from local state and drive to completion — no re-asserting prior hypotheses, no defensive explanation of earlier missteps, and no pausing for permission when the task is already authorized. Confidence: 0.8
- Runs the same verification ritual before each deploy: py_compile + git diff --check + focused pytest, then the canonical .bat wrapper; uses wrapper scripts rather than direct python remote invocation, and cleans up temp helper logs/scripts after analysis. Confidence: 0.9
- When reporting on batches that made no remote/paid calls, expects an explicit account of the local test methodology (unit/integration suites, py_compile, git diff --check, selector/preflight gates) and an honest statement of what local testing cannot prove — remote-only outcomes (e.g., whether a speculative lane is actually consumed in production, or whether local CUDA mechanics predict Modal performance) must be deferred to the authorized remote cycle, never implied as verified. Confidence: 0.7
- Requires an explicit final verdict on the rightness criteria, including a return block with exact run IDs and per-run metrics (E26_RIGHT / FINAL_RUN_1_REQUEST_ID / SPEC_CLIP_CONSUMED / CLIP_HYDRATION_MS / D15_OVERLAP_MS / GPU_FAST_RETURN / OUTPUT_SHA / TOTAL_DEPLOYMENTS_USED / TOTAL_PAID_REQUESTS_USED / FAILED_CYCLES_AND_ROOT_CAUSES); when the performance target is not met, returns E26_RIGHT = NO with the root cause (e.g., a storage-bound read that cannot be hidden under a short setup window) and stops remote work rather than declaring victory or burning cycles on a mechanism with an established ceiling. Confidence: 0.9
- Automatic retry loops must halt when the failure cause is already known: if attempts fail for the same deterministic reason (e.g., no valid snapshot: `cpu_snapshot_models_present=0`, `snapshot_identity` empty), the harness must not keep retrying the identical attempt with cooldowns — stop, diagnose the deployment, and only re-run after the root cause is fixed; retries are only justified for transient/unknown causes. Confidence: 0.95
- Once a blocker's root cause is identified and a concrete recovery route exists (e.g., fresh app registration to force the construction lifecycle), must execute that route and iterate until the completion gates actually close — stopping again to re-report the same known blocker as terminal, or finishing with "PARTIALLY COMPLETE / pending valid run / environment blocker / needs implementation batch to measure", is not acceptable. Confidence: 0.85
- Reacts immediately when a command "never returns": a long-running/background shell that hangs (e.g., a piped wrapper that swallows output and never exits cleanly) is flagged by the user as a problem. Avoid launching commands in a way that can hang indefinitely — prefer bounded foreground execution, verify completion via state artifacts rather than the shell's exit, and kill stuck tasks promptly instead of leaving them running. Confidence: 0.8
- When a correction identifies a recurring core failure, demands that remote validation stop and the architecture be fixed first: first trace the existing evidence (persisted run artifacts, not new runs), do not spend more runs confirming a known failure — diagnose from captured evidence, fix the implementation (e.g., the loader regression and the accidental serialization blocking another model's forward) locally, then redeploy and run the next cold validation gate. "No additional blind runs" before the evidence trace is complete. Confidence: 0.9
- Deploy-ownership protocol: when another agent currently owns the deploy loop, the batch must implement and validate locally only — zero remote deploys, zero remote requests — and stop at a local-readiness marker (e.g., READY_FOR_REMOTE_PARITY_GATE) until the user explicitly grants deployment ownership; never compete for the deploy target. If not the current deploy owner, deploying or running Modal requests is forbidden — prepare the remote validation plan only and wait for permission. This is a hard rule the user re-states explicitly in every batch prompt: an agent that is the designated deploy owner must use the canonical tool (v2ctl) and ONLY it, and must not invent BAT wrappers, PowerShell set-&&-call chains, semantic flag whitelists, or other flag-forwarding mechanisms; when the user withholds permission, the agent must stop at local readiness, state exactly what remains unresolved, and wait — no paid/remote work. Confidence: 0.9
- Source-control discipline before any editing in a shared repo: capture `git rev-parse HEAD`, `git branch --show-current`, `git status --short`, `git diff --stat` first; never create a branch/worktree, stash, reset, revert, clean, commit, push, or discard unrelated changes; re-read files immediately before editing; prefer new files over overwriting concurrent agents' work. Confidence: 0.9
- Deploy-health truthfulness is mandatory: a deploy exit 0 proves only transport (`deployment_transport_status = deployed`); runtime health stays `unverified` until the first gate/run actually observes the container running (or a crash loop) — never describe a deployment as HEALTHY from the BAT exit code alone, never pretend a tool can observe remote lifecycle failures it cannot (audit what the deploy backend can/cannot see), and encode the transport-vs-health split (health_check_note, gate as health-validation boundary) in the tooling with tests. Requires per-attempt deploy status AND runtime health status recorded separately in the chronological validation record. Confidence: 0.85
- Deploy-failure masking is unacceptable: a deploy wrapper must propagate the real Modal CLI failure and never report success on a deploy that did not actually update the app — harden the canonical tooling so (a) a failed deploy unlinks its "deployed" manifest so gate/run cannot treat it as valid, (b) the wrapper detects error markers (Modal `+- Error` box, `Traceback`, `charmap`/codec crash) in the captured deploy log even when the CLI exits 0, and (c) deploy success is verified by the app's deployment version ADVANCING (modal app history), not by exit code alone. An exit-0 deploy with no version bump is a failed deploy and must fail loudly. Confidence: 0.85
- Deploy version-advance verification must be a strict pre/post comparison, not recency: capture the app's highest deployment version number BEFORE the deploy and require a strictly-greater number AFTER — a "a version was deployed within the last N minutes" check falsely passes when a no-op deploy follows a real one (observed in the E29 batch: a deploy that left the app unchanged was wrongly accepted). Version reads must use the ACTIVE workspace's credentials, never the raw `modal` CLI profile, which can resolve to a different workspace and silently validate a no-op. Confidence: 0.85
- Deploy-health semantics include a source-identity axis: keep `deployment_transport_status` / `runtime_health_status` / `source_identity_status` distinct, and a deployment is not fully validated until a no-generation source probe proves the remote bytes equal the expected local source (TRANSPORT_DEPLOYED → SOURCE_UNVERIFIED → SOURCE_VERIFIED → RUNTIME_GATE_VALIDATED); a manifest must never flip to "source verified" from the BAT exit code alone. Confidence: 0.8
